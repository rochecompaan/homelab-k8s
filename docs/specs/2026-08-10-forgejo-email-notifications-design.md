# Forgejo Email Notifications Design

## Goal

Enable trusted outbound email from the homelab Forgejo instance for account messages and repository activity notifications.

Forgejo will submit authenticated mail to `mail.upfronthosting.co.za:587` with STARTTLS. Messages will use `forgejo@git.compaan.cloud` as both the visible sender and envelope sender. Email notifications will default to enabled while remaining user-configurable.

## Current state

Forgejo is deployed by the `forgejo` ArgoCD Application using Forgejo Helm chart `17.1.3`, which packages Forgejo `15.0.5`. The current Helm values do not configure a mailer.

The repository already uses `pass`, `just`, Sealed Secrets, and the Forgejo bootstrap Kustomization for credentials. The SMTP password is available locally through `pass show FORGEJO_SMTP_PASSWORD`.

The external Debian mail host runs Exim 4.92 with split configuration. Port 587 advertises STARTTLS and authenticated SMTP, but currently presents a self-signed certificate that expired on March 6, 2020. Apache and Certbot already obtain another, unrelated Let's Encrypt certificate with the Apache authenticator. That certificate does not cover `mail.upfronthosting.co.za`.

## Architecture

The work has two ordered parts:

1. repair the external SMTP endpoint so it presents a valid, publicly trusted certificate; and
2. enable the Forgejo mailer through this repository and let ArgoCD reconcile it.

Forgejo must not be configured to bypass SMTP certificate validation. The GitOps rollout begins only after a normal TLS client validates the repaired endpoint.

## SMTP certificate

### ACME validation

Varnish owns public port 80 and already routes `mail.upfronthosting.co.za` to the Apache backend on port 81. Add `/etc/apache2/sites-available/mail.upfronthosting.co.za.conf` as a minimal, HTTP-only Apache port-81 virtual host and enable it through Debian's normal site mechanism. Invoke Certbot's Apache authenticator with `--http-01-port 81` so it selects that backend vhost; Let's Encrypt still validates through public port 80 and Varnish. Varnish and the separate nginx ACME catcher remain unchanged.

Request a dedicated certificate lineage for only `mail.upfronthosting.co.za`. The resulting files are:

- `/etc/letsencrypt/live/mail.upfronthosting.co.za/fullchain.pem`; and
- `/etc/letsencrypt/live/mail.upfronthosting.co.za/privkey.pem`.

The existing multi-domain `gazette.co.za` lineage remains unchanged. Coupling the mail hostname to that unrelated certificate would make renewal failures affect unrelated services.

### Exim integration

Certbot's `live` and `archive` trees remain root-only, while the Exim daemon runs as `Debian-exim`. Do not grant Exim direct access to the Certbot tree. Instead, combine the renewed full chain and private key into `/etc/exim4/exim-letsencrypt.pem`, owned by `root:Debian-exim` with mode `0640`.

Because Debian's Exim installation uses split configuration, define `MAIN_TLS_CERTKEY = /etc/exim4/exim-letsencrypt.pem` in `/etc/exim4/conf.d/main/000_localmacros` rather than editing `/var/lib/exim4/config.autogenerated`. Debian's package configuration already enables TLS and supports a combined certificate/key PEM.

Regenerate and validate Exim's effective configuration before reloading the service. Confirm `tls_certificate` resolves to the combined PEM; `tls_privatekey` remains unset because the same file contains the key. Keep `/etc/exim4/exim.crt` and `/etc/exim4/exim.key` unchanged for immediate rollback only.

Install `/etc/letsencrypt/renewal-hooks/deploy/install-exim4-mail-certificate` as a Certbot deploy hook. For the matching lineage, the hook creates a same-filesystem temporary combined PEM, verifies that its certificate and private key match, enforces `root:Debian-exim` mode `0640`, validates Exim configuration, retains a hard-linked rollback copy, atomically replaces the Exim PEM, and reloads Exim. A failed pre-install check does not replace the active PEM or reload Exim; a failed reload restores the previous PEM and reloads it.

## Forgejo mailer configuration

Add the following non-secret behavior to the Helm values in `argocd/base/forgejo/app.yaml`:

- mailer enabled;
- protocol `smtp+starttls`;
- SMTP address `mail.upfronthosting.co.za`;
- SMTP port `587`;
- SMTP username `forgejo`;
- visible sender `Forgejo <forgejo@git.compaan.cloud>`;
- envelope sender `forgejo@git.compaan.cloud`;
- repository notification mail enabled through `service.ENABLE_NOTIFY_MAIL`; and
- default user email notifications set to `enabled` through `admin.DEFAULT_EMAIL_NOTIFICATIONS`.

Users retain their own notification preferences. Registration remains disabled, and no existing Forgejo session or Actions behavior changes.

The chart's `gitea.additionalConfigFromEnvs` value injects only the password as `FORGEJO__MAILER__PASSWD`. Environment-backed configuration has higher precedence than ordinary `gitea.config` values and keeps the password out of the ArgoCD Application.

## Secret flow

Create a namespace-scoped SealedSecret manifest at `argocd/homelab/forgejo/bootstrap/mailer-secret.yaml`. It decrypts to a Secret with:

- name `forgejo-mailer`;
- namespace `forgejo`; and
- data key `password`.

Add a `seal-forgejo-mailer-secret` recipe to `Justfile`. The recipe will:

1. read the first line from `pass show FORGEJO_SMTP_PASSWORD`;
2. reject an empty password;
3. write plaintext only to a mode-`0600` temporary file that is removed on exit;
4. create the Secret manifest locally with `kubectl --dry-run=client`;
5. seal it with the configured Sealed Secrets controller; and
6. atomically replace only `mailer-secret.yaml`.

The SMTP username is a non-secret constant and remains in Helm values. No SMTP credential appears in chat, shell tracing, committed plaintext, or command-line arguments.

Add `mailer-secret.yaml` to the Forgejo bootstrap Kustomization. The existing admin-secret recipe rewrites that Kustomization, so its generated resource list must also retain `mailer-secret.yaml`.

Add `homelab.compaan.cloud/forgejo-mailer-secret-revision: "1"` as a versioned Forgejo pod annotation. Incrementing its integer string in the same Git change as a credential rotation causes a declarative Deployment rollout. Direct `kubectl rollout restart` commands are not permitted.

## Sender authorization and deliverability

Before declaring delivery ready:

- confirm Exim permits SMTP user `forgejo` to send with the selected visible and envelope sender;
- determine the existing outbound IP, DKIM signer, and selector;
- ensure SPF authorizes the outbound path for the envelope sender domain;
- ensure the DKIM signing domain aligns with `git.compaan.cloud` under the chosen DMARC policy; and
- publish or verify an applicable DMARC policy.

The received preflight message proves Exim signs with selector `mail`, domain `git.compaan.cloud`, and active key `/etc/exim4/dkim_rsa.private`; the outbound IP is `129.232.177.170`. Preserve the existing `git.compaan.cloud` CNAME to `compaan.cloud` and publish these records in the `compaan.cloud` zone:

- apex SPF: `v=spf1 ip4:129.232.177.170 -all`;
- `mail._domainkey.git` DKIM: the public key derived from the active Exim signing key; and
- `_dmarc.git` DMARC: `v=DMARC1; p=reject; adkim=s; aspf=s`.

No other service sends with an `@compaan.cloud` envelope sender, so the apex SPF policy is intentionally strict. Successful SMTP submission alone is not sufficient evidence of deliverability; a fresh received message must report aligned SPF, DKIM, and DMARC passes.

## Rollout

1. Add the Apache ACME virtual host and obtain the dedicated certificate.
2. Install the Certbot lineage into the combined Exim PEM, select it with `MAIN_TLS_CERTKEY`, validate the generated configuration, and reload Exim.
3. Verify the public port-587 certificate and run a Certbot renewal dry-run.
4. Confirm sender authorization and mail-authentication DNS.
5. Generate the Forgejo mailer SealedSecret locally.
6. Add the Forgejo Helm values, bootstrap resource, recipe, documentation, and rotation annotation.
7. Render and validate the local configuration.
8. Commit and push the repository changes so ArgoCD performs all cluster mutations.
9. Send an administrative test email and one real repository notification.

## Failure and rollback behavior

- If ACME issuance fails, Exim remains on its existing configuration and Forgejo mail is not enabled.
- If Exim configuration validation fails, do not reload the service.
- If combined-PEM validation or permission checks fail, leave the active Exim PEM unchanged.
- If the SealedSecret has not produced its Secret yet, the Forgejo pod cannot consume the password; ArgoCD and the Sealed Secrets controller reconcile it without manual cluster mutation.
- SMTP authentication, TLS, or queue failures are diagnosed through Forgejo and Exim logs. Certificate verification remains enabled.
- Forgejo mailer changes are rolled back with Git. If the external TLS integration fails after issuance, disable Forgejo submission while repairing or reissuing the trusted certificate; do not restore the expired self-signed certificate as a steady state.

## Security

- Commit only SealedSecret ciphertext.
- Keep the SMTP password in `pass` and short-lived mode-`0600` temporary storage during sealing.
- Use STARTTLS with normal hostname and CA verification.
- Do not use Forgejo's `FORCE_TRUST_SERVER_CERT` option.
- Keep the Certbot tree root-only. Copy only the required mail lineage into the atomic combined Exim PEM with `root:Debian-exim` mode `0640`.
- Keep all homelab Kubernetes mutations GitOps-only.

## Verification

This work changes static configuration and integrates with an external SMTP server. A new automated test would not prove end-to-end behavior and is not justified by the Testing Value Gate. Verify directly by:

1. validating Apache and Exim configuration before reload;
2. confirming the public STARTTLS chain, hostname, and expiry for port 587;
3. confirming `exim4 -bP` reports the combined Exim PEM and `Debian-exim` can read it;
4. running a Certbot renewal dry-run;
5. rendering the Forgejo bootstrap Kustomization;
6. rendering the Forgejo Helm chart and inspecting mailer values and Secret references without exposing the password;
7. confirming ArgoCD reaches a healthy synchronized state;
8. sending Forgejo's administrative test email;
9. triggering one watched-repository notification; and
10. checking the received message headers for successful SPF, DKIM, and DMARC evaluation.
